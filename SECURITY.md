# Security notes for this local hardening branch

This describes the intended credential behavior of this branch. It is not an audit, and it is not a claim of zero risk or a sandbox.

## Saved readings

The last successful reading per allowed provider is saved in the app's preferences (`lastReadings.v1`) so the notch is not blank after a restart. It holds usage windows, plan, Grok billing figures and the reading time only. The account name, live sessions and the account key are not written. A saved reading is shown dimmed with its age until a new reading replaces it. When the owning tool's sign-in has expired, the last reading stays up, dated, with a note that it updates when that tool is next used. Turning a provider's access off deletes its saved reading.

## What can read a sign-in

A new installation starts with no usage access. `Preferences.usageAccessProviders` defaults to empty and is stored separately from `hiddenProviders`. A provider that was only visible before is not authorized.

After the user turns on **Allow usage access** for one provider, refresh may read that provider's existing local sign-in. A token is sent only to that provider's usage URL.

- Claude: existing Keychain item `Claude Code-credentials`. The one foreground read returns the whole credential record. The app immediately keeps only `accessToken` and expiry from `claudeAiOauth` in a RAM session and drops the raw record, so a refresh token is not selected, stored, copied, or used. Later refreshes reuse that RAM session until it is missing or expired. Expiry reads the current access token again and does not use a refresh token. The session is cleared on revoke, expiry, needsAuth (including HTTP 401 or 403), or process exit. A needsAuth failure leaves the saved allow switch on and clears only RAM. The status stays visible for a manual action. The next background read can load the current item silently and does not open a dialog. Other network failures keep the RAM session. RAM is ordinary process memory and is not promised to be securely erased. It is not written to disk or back to the Keychain. The app does not refresh tokens. Live session and project metadata are not read; the usage snapshot's session list is empty.
- Codex: `~/.codex/auth.json` when it is readable, otherwise the existing `Codex Auth` Keychain item. The Keychain path keeps only an OAuth `tokens.access_token` and optional `account_id` in the RAM session. `OPENAI_API_KEY` is not sent to the usage endpoint. Rollout files, the Codex state database, and conversation logs are not scanned.
- Grok (stored as the `grokBuild` provider id, so an existing Grok Build approval carries over): `~/.grok/auth.json` only after that provider is allowed. The parser accepts a single live access token whose dictionary key issuer is exactly `https://auth.x.ai`. If `oidc_issuer` is present it must be that same issuer. Lookalike issuers, conflicting issuer metadata, a missing or expired `expires_at`, and more than one live trusted entry fail closed with a Grok CLI sign-in prompt. `refresh_token`, client id, and email are not kept. When the access token is a JWT, its payload is decoded locally without verification only to take `sub`; the app keeps the SHA-256 of `grok-sub:` plus that subject as a RAM-only account key, never the subject itself, and never displays, logs, encodes or persists the key. It is compared with the key of the last reading so a failed refresh after an account switch does not keep showing the previous account's usage; a missing key on either side counts as a mismatch. Before a refresh failure is applied, the same auth file is read again locally for that comparison; nothing is sent. The app does not renew the token or write the file itself. When no live token is found, it runs the installed Grok CLI (`/opt/homebrew/bin/grok`, `/usr/local/bin/grok` or `~/.local/bin/grok`) as `grok models`, at most once every 10 minutes, with a 30-second timeout and output discarded. That command sends no prompt; the CLI renews its own sign-in with its own refresh token and writes its own file, which the app then reads as above. The app still never reads the refresh token. The access token is held only for that request and is sent only as `Authorization: Bearer` plus `X-XAI-Token-Auth: xai-grok-cli` to `https://cli-chat-proxy.grok.com/v1/billing?format=credits`. API keys, browser cookies, activity scans, and transcripts are not used. The response is the shared weekly allowance used by Grok Build, Grok Bot and Cursor. The card shows the overall percentage, the per-product percentages the server reports, and prepaid, on-demand and top-up fields only when present; unknown is never shown as zero. Cursor's own endpoint and Grok Bot's local cache are no longer read.

Launch keeps the saved usage-access set as it was stored. The default is still empty, and startup does not call Security. Claude and Codex stay allowed across an ordinary restart of the same binary when the user left them on. The saved value is only the provider id, never a token. A separate non-secret refusal flag records an explicit keychain denial and blocks later background reads until a successful foreground approval clears it.

Turning a live switch on is the only Keychain prompt. Each approval performs one `SecItemCopyMatching` read. That OS read keeps its own ticket until the original call returns, including success, failure, or a sanitization failure. Invalidating the epoch or discarding the session does not remove the ticket and does not start another read. A second grant is refused while the ticket exists, including when Settings is recreated or the epoch was already bumped, so prompts are not queued. After the original call completes or fails, a later grant may start. Closing Settings or turning the switch off bumps that service's grant epoch immediately and does not wait on the OS read. Closing Settings also discards a session whose switch is still awaiting UI approval, including when the store already sanitized it and the main actor has not applied it. A session that is already enabled, with no approval in progress, stays. A stale result cannot commit, cannot clear a newer session, and cannot turn the switch on. A failed read clears only its own generation. Claude always requests read access to `Claude Code-credentials`. Codex requests read access to `Codex Auth` only when `~/.codex/auth.json` is not already readable. That call may show the macOS prompt and performs one `SecItemCopyMatching` read for that reconnect. Claude keeps access token and expiry. Codex keeps `tokens.access_token` and, when present, `account_id`. Nothing else from the record is retained. The sanitized session lives only in RAM for this app process. It is not written to disk, UserDefaults, or back to the Keychain. A missing, cancelled, or invalid record is not a grant: that attempt's generation is cleared and the switch stays off. A cancelled or refused foreground prompt stores the refusal flag immediately and does not try `/usr/bin/security`. A stale completion does not erase a newer session. Closing Settings cancels only a foreground approval still in progress. It does not cancel a background read for a provider that is already enabled. An earlier build discarded that foreground read and then read again for refresh, so Allow could be followed by a second prompt. Background `Keychain.data` runs only when the saved allow-list contains the mapped provider and the refusal flag is false. That check happens before any Security call. Unknown services return nil. Claude Code-credentials maps to Claude and Codex Auth maps to Codex. A valid sanitized RAM entry is reused. A miss or an expired entry uses the same grant ticket and reads the current item silently: the process-wide interaction switch is turned off for that call, restored to its previous value, and `kSecUseAuthenticationUIFail` is set. If that setup fails, the read stops. A silent auth or interaction refusal, and only that, may retry through `/usr/bin/security` with the exact service and the exact account from the caller or from one matching allowlisted item. Several matches, a missing account, a locked keychain, or a status error skip the tool. The attribute query lists metadata for that one allowlisted service only. It is not a list of the whole Keychain. The newest match is chosen by modification date and read by its persistent ref. There is no service-only command. The tool is the literal executable `/usr/bin/security` with `find-generic-password -s <service> -a <account> -w`. That command cannot take a persistent ref, so a duplicate under the same account can be an older item. An expired payload from that command fails closed and is not kept. Its stdout is capped, its stderr is discarded, and a timeout terminates then kills the child. The password is sanitized in process. Nothing secret is written to disk, UserDefaults, or the log. The log records only that an approved direct or tool read completed. Direct success does not launch the tool. Background failure does not open a dialog; the status asks for a manual switch off and on. HTTP needsAuth clears the RAM session only and does not remove saved consent. A partition list that admits only Apple tools can still serve a later silent read after one approval. A future ad hoc rebuild may need one foreground OS grant again. An ordinary restart of the same binary is intended to keep working from the saved allow-list. That restart behavior is not claimed as proven until a live coordinator check says so. Grok has no Keychain grant. The foreground helper returns without a Security call for it. The allow switch does not call Security on the main actor; the grant runs detached, and a repeated click or a turn-off while it is in flight cannot start a second prompt or apply a late success.

Demo mode ignores the allow-list and shows sample providers. It returns before Keychain and HTTP.

## What this build does not do

- No in-app Claude sign-in, sign-out, browser OAuth, loopback callback, token refresh, bootstrap, or saved Claude session. `signIn` and `refresh` fail immediately in every build. Older authorize-URL helpers remain only so parser tests still compile.
- No in-app Claude sign-in path reads or refreshes a refresh token. Keychain writes throw. Deletes do nothing. Unknown services are rejected before Security. Demo returns before Security. Nothing is copied between keychain stores. The app does not list every Keychain item. It reads attributes only for an allowlisted service. Silent background reads do not prompt. There is no rollout or conversation scan, no Claude session metadata read, and no API-key fallback for Codex quota.
- Keychain helper reads only `Claude Code-credentials` and `Codex Auth`. The first read is a foreground `SecItemCopyMatching` when the user turns usage access on. Later reads of an approved, non-refused provider may use a silent `SecItemCopyMatching` and, only after a silent refusal, `/usr/bin/security` for that exact item. No credential copy is saved. Direct background reads explicitly suppress Keychain UI. The approved Apple-tool fallback relies on the existing item access controls and has a bounded timeout; two same-build restart checks on 2026-10-24 completed automatically without a new approval action. This verifies that local item and build, not every future OS access-control change. A locked default keychain does not start that tool.
- No snapshot cache. `lastGoodReadings` is not read or written. Disconnect cancels that provider's task, drops its in-memory snapshot and limit events, and ignores a late result via a per-request generation id, including across disable and re-enable. Cancellation alone is not the guarantee. In-memory readings can still exist while an allowed provider stays enabled.
- HTTP allows only `https://api.anthropic.com/api/oauth/usage`, `https://chatgpt.com/backend-api/wham/usage`, and exactly `https://cli-chat-proxy.grok.com/v1/billing?format=credits`. The query exception is that one absolute string. Any other query, extra parameter, scheme, host, path, userinfo, port, or fragment is rejected before a session is used. Sessions are ephemeral, with cookies, URL cache, and credential storage disabled. Redirects are rejected. Demo throws before a request. Errors do not include credentials. Grok web chat is not implemented and is not described as a quota source.
- HTTP 429 is not treated as a failed read. The provider waits out `Retry-After` (clamped to 30 seconds through 15 minutes, 120 seconds when absent) before sending another request, including on a click, and a reading stays bright for five minutes before it dims. Logs record only the provider id and a fixed failure kind such as `HTTP 503`.
- Sparkle starts only in Release builds, which are the signed and notarized downloads. It reads `https://neeeeeeessa.github.io/agent-notch-plus/appcast.xml` and installs an update only when its EdDSA signature matches the public key in `Config/Info.plist`. Debug and `AGENTNOTCH_DEMO` builds never start Sparkle, and their update menu items stay disabled.
- Login-item controls are hidden, so this build does not offer launch-at-login registration. Placement and presence controls remain.

## Residual risk

An enabled provider still uses a powerful existing token. Those tokens are not usage-only. The process is not sandboxed by this change. A bug in request construction, redirect handling, or a provider parser can still expose or misuse a token the user chose to allow. Disconnect stops later publishes from this app; it does not revoke the token at the provider.

Local checks on 2026-10-24 loaded all five providers of the earlier build, which passed 122 hardened and 132 demo fixture tests. The three-provider revision removes Cursor and Grok Bot reads. Two same-build application restarts then preserved the saved Claude approval, read the existing sign-in through the local Apple Keychain tool, and completed Claude usage fetches without a new approval action. The second run completed its usage fetch on an automatic retry. Only fixed provider-status and read-route events were inspected; no credential values were printed. Native UI control was unavailable, so the owner explicitly authorized Terminal restarts and non-secret log checks. Legacy app-owned Keychain items and files, if any remain from older builds, are left in place. Deleting them needs an explicit owner decision. The same is true of Codex session logs and Claude Code's own credential item: this build does not modify them.

`AGENTNOTCH_DEMO` builds keep the sample-data path. Hardened non-demo builds start with an empty allow-list in a new preferences domain and preserve existing explicit approvals. OAuth paths remain retired as described above.

## Verification without account access

Prepare the installed app from a separate build-only derived-data directory, not a test product. Replace a stopped app bundle cleanly instead of merging a directory copy over it: an old `PlugIns/AgentNotchTests.xctest` can otherwise survive and invalidate the new signature. Run `codesign --verify --deep --strict <installed-app>` as a separate checked step and require its successful exit before launching.

Use a fresh bundle identifier for every test run, rather than the identifier of the app being used with real accounts. A new preferences domain starts with the usage-access set empty. Use `-only-testing:AgentNotchTests` for the full target; a method selector without the Swift Testing identifier syntax can select zero tests while xcodebuild still reports success.

Read the generated xcresult with `xcrun xcresulttool get test-results summary --path <result.xcresult>`. Acceptance requires `result` to be `Passed`, `totalTestCount` to be greater than zero, and `failedTests` to be zero. `TEST SUCCEEDED` alone is insufficient. The synthetic provider and HTTP policy tests do not validate real accounts or endpoint compatibility. Grok tests use synthetic JSON and temporary directories only. No real home cache, auth file, or token was read for this change, and live account behavior has not been verified.

For the recorded negative control, only a disposable copy was changed: the early `isEnabled` guard in `UsageStore.refresh` was bypassed, and the full target ran with `AGENTNOTCH_DEMO` under another fresh identity. `emptyAllowListDoesNotFetch` failed on a forbidden fake fetch. Never run that mutation with real providers or against the active app's preferences.
